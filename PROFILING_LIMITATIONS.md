# Profiling limitations and requirements

This release implements an **import-first** deep profiler and server-API controlled experiments. It does not claim a completed live Nsight capture.

- Optional NVIDIA [Nsight Compute](https://developer.nvidia.com/nsight-compute) produces reports. Export an existing report using `ncu --import capture.ncu-rep --page raw --csv --units base` and save clean CSV output. The app accepts the documented long-form raw schema, not summary/wide/localized formats or proprietary binaries. No installed ncu version was executed during validation.
- CUDA execution, GPU architecture compatibility, CUPTI, performance-counter permission and available metric/section lists require real tool/device probes and are Unverified. PATH absence means Not detected, not proof a tool is uninstalled. Found files are not executed during discovery. NVML can establish driver/device visibility only. Permission-denied responses never trigger elevation or restriction bypass.
- Counter availability varies by architecture, driver, profiler and permissions. Nsight may instrument and replay kernels, perturbing timing and cache state. Imported results are not directly comparable to ordinary inference throughput. Profiler version, capture timestamp/duration, requested metric set, capture GPU and workload are not authenticated by CSV. The currently selected model/backend is contextual metadata, not verified attribution.
- No attachment to Ollama or unrelated processes; no live profiler launch, child-process tree or temporary capture artifacts. Child cleanup, live capture cancellation and profiler crash recovery therefore remain unimplemented rather than tested successfully. Imports have bounded synchronous parsing on a worker; cancellation discards the result after completion.
- `llama-bench` integration was investigated against the official README. It documents `-m`, `-p`, `-n`, `-r`, `-o json`/`jsonl` and JSON timing fields. No local binary/version/output was verified, so direct execution/import is deferred. Its synthetic prompt/token tests have different semantics from server inference; tokenization and sampling timing must be verified before comparison. PATH availability alone does not enable it.
- Server experiments cannot set or verify quantization, batch size or GPU offload. Effective context/truncation, sampler implementation and prompt-cache state are not fully controlled. Output lengths are requested caps; early EOS can produce fewer tokens. Context curves use reported prompt tokens and do not isolate attention time. No universal model/device performance claim follows from these samples.
- Exact weight reads, source-level mathematical execution classification, host/device copy attribution, attention-kernel timing and theoretical peak bandwidth are unavailable. Tensor usage is not inferred from GGUF labels or names. Only occupancy has a conservative evidence rule; other causal diagnoses require more evidence.
- Fully normalized per-kernel SQL tables, profiler-to-profiler comparison, advanced counter-specific visualizations and architecture metadata discovery remain future work. The detailed JSON preserves measurements for inspection/export.
- Native save dialogs, revised page layout and real-model experiment execution were not manually exercised in this phase. Automated synthetic fixtures are test-only. Previous owner-verified Phase 01/02 workflows remain the established baseline, not newly re-certified live behavior.
- Windows native tests are the automated platform baseline. Linux runtime testing is explicitly deferred to final cross-platform validation. Shared Rust/TypeScript architecture and existing Linux loader/platform branches are preserved.
